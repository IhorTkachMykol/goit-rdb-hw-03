# HW2 — Проєктування схеми БД для ML feature store

Домашня робота з курсу **Relational Databases for Data Science** (Тема 2:
ER-моделювання, нормалізація, point-in-time correctness, feature store).

Сценарій: прогноз відтоку (churn) підписників відеосервісу — модель щодня
оцінює, чи перестане користувач дивитися контент протягом наступних 30 днів.

## Джерело даних

Це **не** Northwind і не інший публічний датасет. Дані — синтетичні, написані
вручну спеціально для цієї роботи, щоб продемонструвати:

- природний зв'язок **N:M** між користувачами й тайтлами (`hw2_viewings`);
- історію ознак з інтервалами чинності `[valid_from, valid_to)`
  (`hw2_user_features_offline`);
- **point-in-time correct** приєднання ознак до training events
  (`hw2_training_events`);
- денормалізований online-шар для швидкого lookup (`hw2_user_features_online`).

Значення підібрані вручну так, щоб покрити граничні випадки (подія рівно на
межі двох версій ознаки, подія до появи першої версії, відкрита версія без
`valid_to`) — це не імітація реального трафіку, а мінімальний набір, що
доводить коректність часової логіки.

## Структура вибірки

| Таблиця | Рядків | Опис |
|---|---|---|
| `hw2_genres` | 4 | довідник жанрів |
| `hw2_titles` | 6 | фільми/серіали, кожен належить одному жанру |
| `hw2_users` | 4 | користувачі (`user_id` 1, 2, 7, 42) |
| `hw2_viewings` | 14 | факти перегляду (bridge-таблиця users ↔ titles) |
| `hw2_user_features_offline` | 12 | історія ознак; у користувача `1` — 4 версії, у `2` і `42` — по 3, у `7` — 2 |
| `hw2_training_events` | 11 | label-події з `prediction_ts` і `churn_in_horizon` |
| `hw2_user_features_online` | 4 | по одному поточному рядку на користувача, заповнюється матеріалізацією з offline-шару |

Усі часові мітки — `TIMESTAMPTZ` з явним `+00` (UTC).

## Інструкція із запуску

Notebook розрахований на **Google Colab**, оскільки перша клітинка ставить
PostgreSQL через `apt` (потребує root-доступу до ОС; на звичайному
Jupyter/локально працює так само, якщо є `sudo`).

1. Відкрийте `HW2_RDB_feature_store.ipynb` у Google Colab
   (File → Upload notebook, або перетягніть файл на colab.research.google.com).
2. Виконайте **Runtime → Restart session and run all**.
   - Перша клітинка ставить і запускає PostgreSQL через `apt`, задає пароль
     користувачу `postgres` і підключається через SQLAlchemy
     (`postgresql+psycopg2://postgres:postgres@localhost/postgres`).
     Перший запуск триває ~30–60 секунд.
   - Далі клітинки виконуються послідовно: ER-діаграма → DDL → завантаження
     тестових даних → нормалізація/матеріалізація → point-in-time запити →
     Reflection → підсумкова перевірка.
3. Notebook самоперевіряється: майже кожна клітинка завершується `assert`,
   який падає з поясненням, якщо щось пішло не так. Якщо всі клітинки
   виконались без `AssertionError` — робота відтворена коректно.
4. Схема ідемпотентна: на початку є `DROP TABLE IF EXISTS ... CASCADE`, а
   завантаження даних використовує `TRUNCATE ... RESTART IDENTITY`, тож
   notebook можна запускати повторно без ручного очищення.

### Типові проблеми

- **`ModuleNotFoundError: No module named 'pgserver'`** — застаріла версія
  клітинки 0; переконайтеся, що використовуєте поточний файл (перша клітинка
  має починатися з `!apt-get -qq update && apt-get -qq install -y postgresql`).
- **Помилка підключення до `localhost/postgres`** — перевірте, що
  `!service postgresql start` у клітинці 0 виконався без помилок; на деяких
  образах Colab сервіс може вимагати повторного запуску клітинки.
- **Версія PostgreSQL** залежить від пакета в образі Colab (зазвичай 14–16);
  вона друкується в кінці клітинки 0. Уся схема і запити сумісні з
  PostgreSQL 11+.
